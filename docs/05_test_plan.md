## 1. テスト方針

### 1.1 検証手段の切り分け

| 区分 | 記号 | 内容 | 本環境で可能か |
| --- | --- | --- | --- |
| 自動 | **自動** | Vitest（単体）、Vitest + supertest（API。SQLite をテストごとに生成）、Playwright（ヘッドレス Chromium。WebGL は SwiftShader、カメラは `--use-fake-device-for-media-stream` + `--use-file-for-fake-video-capture=<ターゲット画像を動画化した .y4m>`）。リポジトリにテストコードとして残し、再検証（リグレッション）で再実行する | 可 |
| 手動 | **手動** | 本環境で QA が Playwright スクリプト / curl / `sqlite3` / ファイル検査 / Lighthouse を使って 1 回ずつ実施し、結果（スクリーンショット・応答・数値）を QA レポートに貼る。自動化の費用対効果が低いもの、目視判断が要るもの | 可 |
| 実機 | **実機** | iPhone（iOS 16 以上、Safari）と Android（Android 10 以上、Chrome）で、印刷した見本をカメラにかざして確認する。**本環境ではカメラ・画像トラッキング・QR の実読み取り・LINE アプリ・実回線・fps は検証できない**ため、オーナーに §5 のチェックリストで依頼する | 不可（オーナー依頼） |

本環境でできないことの明示（要件定義 §3.3、§9.2 と整合）:

- iOS Safari / Android Chrome の **カメラ起動・画像トラッキングの品質・追従 fps**（AC-M1(3)、AC-M4(2)、AC-K3、NFR-2(c)(d)(e)）。
- 標準カメラアプリ / Google レンズによる **QR の実読み取り**、**LINE アプリ内ブラウザ**の挙動、**LINE スキームでアプリが開く**こと（AC-M4(1)(5)、AC-M3(2)）。
- **4G 相当の実回線**での所要時間（AC-M4(4)）。本環境では CDP のネットワークスロットリングと Lighthouse で近似値を測り、実機の値と併記する。
- **動画の音声**が実際に鳴ること（AC-M4(3)）。本環境では属性（`muted` / `playsinline`）と状態遷移のみ検証する。
- **AC-K7（未経験者 3 名の 30 分テスト）**。マーケター推薦のテスターをオーナー側で手配し、QA は計測シートと集計を担当する。

### 1.2 自動テストの前提と注意

- ヘッドレス Chromium の MindAR 認識はフェイクカメラ（静止したターゲット画像の `.y4m`）で行う。`04_architecture.md` §3.2 で MindAR の import まで確認済みだが、**フェイクカメラでの認識成功までは未確認**。認識が安定しない場合、TC-M4-07 は「カメラ映像表示・`view_start` 送信まで」を自動、「認識以降」を実機へ振り替え、その旨を QA レポートに記す。
- SwiftShader では `.mind` 生成が実 PC より遅い。NFR-3（60 秒）の判定は参考値とし、合否は手元 PC（Chrome 最新）での手動計測で決める。
- セキュアコンテキスト: Playwright は `http://localhost` でカメラ API が使える。Cookie の `Secure` 属性は HTTPS 配信時のみ検証対象とする（開発用 HTTPS が用意されている場合はそちらで実施）。
- SQLite の検査は `sqlite3` CLI（無ければ `better-sqlite3` を使う Node スクリプト）で行う。

### 1.4 テストの実施順

1. 自動テスト（単体 → API → E2E 作成画面 → E2E 閲覧ページ）を実行し、Blocker / Major を先に起票する。
2. 手動テスト（非機能・セキュリティ・文言）を実施する。
3. Blocker が無い状態で、実機確認（§5）をオーナーへ依頼する。実機確認用に、公開済みプロジェクト 1 件（3 種の印刷見本に対応する 3 プロジェクト）と未公開プロジェクト 1 件を QA が用意し、QR を印刷用 PDF にまとめて渡す。
4. 不具合修正後の再検証は、自動テスト全件 + 修正に関係する手動 / 実機項目のみ。

## 6. 不具合の重要度基準と QA 合格基準

### 6.1 重要度

| 重要度 | 定義 | 例 |
| --- | --- | --- |
| **Blocker** | Must（M1〜M7）または制約 K1〜K5 のいずれかが成立せず、MVP の価値検証（PMF 検証）ができない。回避策が無い | iOS Safari または Android Chrome で体験が起動しない / 追従しない。公開 QR から導入画面が開かない。カメラ映像や画像データがサーバへ送信される。他ユーザーのプロジェクトを閲覧・編集できる。認証無しで変更系 API が通る。計測が記録されない。公開・停止ができない。固定 ID / パスワードが埋め込まれている |
| **Major** | 受け入れ基準（AC）または R1〜R3 を満たさないが、回避策がある、または影響が限定的 | 特定形式（例: WebP）が受け入れられない。「終了しました」画面に R1 のボタンが無い。アプリ内ブラウザで「このまま試す」が無い（R3）。`page_open` / `blocked` が記録されない（R2）。期間指定の境界が JST でない。QR が公開前にダウンロードできない。日本語でない文言が主要画面にある。性能目標 NFR-2(a)(b) を 50% 超過 |
| **Minor** | 体験・作成は成立するが、使い勝手・表記・軽微な表示の問題 | 保存状態表示の遅れ。R4 / R7 / R8 / R9 / R11 の案内文言の不足。アクセシビリティ（axe moderate 以下）。CSV の BOM。レイアウトの軽微な崩れ。性能目標の 50% 以内の超過 |

起票時には ID、重要度、再現手順、期待 / 実際、環境（本環境 / 実機の機種・OS）、対応 TC を書き、`docs/05_qa_report.md` に記録する。要件定義と実装が異なる場合、要件側の曖昧さが原因なら §7 の質問として開発者・マーケターに確認し、合意後に重要度を確定する。

### 6.2 QA 合格基準

以下をすべて満たしたとき QA 合格とし、オーナーの最終確認へ回す。

1. **Blocker が 0 件**。
2. **Major が 0 件**。ただし、マーケターと開発者が「次スプリントへ送る」と合意し `03_review_log.md` に記録したものは除く（R1〜R3 は実装必須扱いのため除外不可）。
3. 自動テスト（§2 の「自動」全件 + §3 / §4 の「自動」）が全件 Pass し、CI またはローカルで再実行可能な状態でリポジトリに含まれる。
4. 手動テストが全件実施済みで、結果が QA レポートに記録されている（Fail は上記 1〜2 の基準で判定）。
5. 実機チェックリスト §5 の 1〜13 が iPhone・Android の **両方** で ○（項目 13 の「このまま試す」でカメラが使えないこと自体は OS 制約のため不合格にしない。案内と導線があれば ○）。14〜15 は実施できた範囲を記録。
6. AC-K5（カメラ映像非送信）が本環境（TC-K5-01）と実機（TC-K5-02）の両方で確認されている。
7. AC-K7（30 分テスト）は結果を記録する。未達（3 名中 2 名に届かない）の場合は Major として改善候補を列挙するが、他の基準を満たしていれば QA 合格とし、オーナーが MVP 公開の可否を判断する（テスターの手配に依存するため）。
8. Minor は件数制限なし。未対応の Minor は一覧にして引き継ぐ。
